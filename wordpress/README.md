# Staging WordPress integration

This plugin is supplied source code. It has **not been installed or executed on Trackier WordPress**. Local frontend tests use a fake API. A real WordPress/PHP staging acceptance run is required before production. It requires PHP 8.0+ and declares WordPress 6.4+; use currently supported patched versions in hosting, not an old minimum merely because it is accepted.

## Install and configure

1. Back up a staging copy of WordPress. Confirm access controls, current plugins/Elementor/theme, PHP version and permalink settings with your WordPress developer. Never test plugin installation by changing the live site first.
2. Copy **only** `wordpress/trackier-react-content/` to staging `wp-content/plugins/trackier-react-content/` using your team's deployment method. Alternatively zip that folder and use Plugins → Add New → Upload Plugin on staging. Activate **Trackier React Content Starter**. The Node project does not belong in `wp-content/plugins`.
3. In Settings → Permalinks, confirm pretty permalinks and that `/wp-json/` works. The plugin defines no frontend rewrite rules, so it does not need a new frontend URL base. If a security plugin restricts REST, explicitly permit only the required published endpoints.
4. In Settings → **React Site Settings**, paste `wordpress/examples/site.json` and save. These are clearly labeled sample values. Replace with approved content before launch. Saving invalid JSON or fields shows an error and retains the previous valid settings.
5. In **React Pages → Add New**, create title “Marketing template — sample”, content key `react-demo`, and paste `wordpress/examples/page.json`. Publish on protected staging. Create another page with content key `reuse-demo` using `wordpress/examples/reuse-page.json`. Slug is in the **Content key (slug)** box; enable it under Screen Options if hidden. The title/slug/timestamp are generated by WordPress and must not be inserted into the editor JSON.
6. Check staging `/wp-json/trackier/v1/site` and `/wp-json/trackier/v1/pages/react-demo`. Successful responses contain the documented JSON, not an HTML login page or redirection. A random slug returns 404 with code `trackier_page_not_found`.
7. In React `.env.local`, select WordPress mode and set the verified API base as described in `docs/setup.md`. Restart the local app. Fetches happen server-to-server, so browser CORS headers are not required for this frontend. Fix actual origin/firewall/auth restrictions; do not enable wildcard CORS to mask a server request problem.

## Central navigation

Under the site's menu administration, assign an existing/approved WordPress menu to **Trackier shared primary navigation**. The plugin uses that menu instead of the JSON navigation array. Assign **Trackier shared first footer column** to override the first footer column's links. If no menu is assigned, the respective JSON content is used.

The primary adapter handles top-level links and one child level. The footer adapter uses top-level links. Grandchildren, special widget data, mega-menu columns/icons and custom link attributes/targets are not modeled. Inventory these before matching the live shell; expand the contract and renderers deliberately. Add custom links using root-relative final public URLs where possible; menu item URLs must be safe HTTPS/root-relative/mailto/tel links.

The plugin registers locations; it does not alter existing menu assignments or Elementor templates. Your Elementor header must use the same WordPress menu, and footer/site settings need dynamic bindings or a developer adapter. Some themes expose menus in different admin locations; your theme/Elementor setup determines the actual UI. This is a required integration step, not something activation can infer.

## Content editing limits

The JSON interface is an initial technical foundation. It provides validation, escaping, permission/nonce checks and preserves the last valid JSON when an edit is invalid. It does not provide a visual builder, media picker, repeaters, revisions or autosave for payloads. Invalid first payloads are kept as drafts. Existing native title/status edits can still save when a JSON edit is rejected; review the warning and current publish state.

Before giving this to a broad editorial team, create labeled controls for this same shape, with previews and revisions. A custom UI avoids plugin dependence; an approved fields plugin can be worthwhile for media selection and repeaters. Those fields should map into this stable API so React does not depend on their database format.

Empty `testimonials`, `features.items`, or `faq.items` are allowed and hide the associated content where appropriate; parent headings/objects remain part of the schema. Optional images/secondary CTA can be omitted entirely. Alt text can be empty only when an image is decorative. Images must have positive intrinsic dimensions; remote image URLs must be HTTPS raster files. Local `/react-assets/*` URLs are only useful where those frontend assets exist.

Page titles and slugs live natively in WordPress. To change a public URL, coordinate with the developer who maintains the route registry and redirects. Do not assume editing a slug automatically transfers public path ownership.

## Publication and security

- The post type has no WordPress frontend permalink, archive, search listing or public core REST collection. Explicit custom endpoints return published, non-password-protected records only.
- Draft, private, scheduled and password-protected content is unavailable even when adding `context=edit` to the public endpoint. Authentication/preview support is intentionally absent.
- Public site/page endpoints use explicit public permission callbacks. WordPress admin changes require normal logged-in capabilities and nonces. The page type uses page permissions; site settings require `manage_options`.
- Unknown fields are discarded; text is sanitized to plain text. URLs are restricted and frontend runtime validation adds a second boundary. The adapter does not expose raw post meta, user records or Elementor data.
- JSON is public as soon as a React Page is published. Frontend noindex is not access control. Protect staging at its web server and avoid publishing embargoed content to a public API.
- Responses ask upstream caches not to store them; verify WP Rocket/security/CDN behavior for `/wp-json/trackier/v1/*`. The Next server caches public data intentionally. Menu changes and urgent unpublishing need cache invalidation at every relevant layer.
- No WordPress-to-Next webhook, private credentials, or production routing mutations are installed automatically.

For an automatic refresh integration later, a trusted WordPress server hook/job can POST to the frontend's `/api/react/revalidate/` with `Authorization: Bearer <secret>`. Keep the secret in protected server configuration, do not log it, add retries and rate limiting, and trigger after page publication/unpublication, menu changes and site settings saves. Current `REVALIDATE_SECRET` is blank and this endpoint is disabled. Use HTTPS outside localhost. The payload is unused; the endpoint only invalidates a fixed tag.

## Required staging acceptance tests

1. Activate/deactivate the plugin and confirm all existing Elementor pages, REST routes and menus work as before; check PHP logs.
2. Save valid site/page payloads, request their endpoints and compare against the example contract. Test Unicode, apostrophes, multiline text, empty optional arrays and absent optional images.
3. Save malformed JSON, missing fields, `javascript:` links and invalid images. Confirm errors and retention of prior valid content. Confirm an invalid first page does not publish.
4. Use editor/admin accounts and a user without edit permissions. Confirm permission boundaries and that a missing/bad nonce cannot change data.
5. Publish, unpublish, schedule, password-protect and mark a page private; confirm the public endpoint exposes only eligible published content. Check cached removal separately in Next.
6. Assign the shared menus, test one nested level, then remove assignments; confirm documented overrides/fallbacks and no silent alteration of existing Elementor selection.
7. Test image/SEO values, the actual API origin from the Next host, query endpoints, redirects and web-server logs. API redirects are intentionally rejected by the frontend to expose origin routing mistakes.
8. Confirm no duplicate frontend WordPress URL, sitemap entry, archive or feed is produced for React Pages, including third-party SEO plugin behavior. Core defaults cannot guarantee every plugin's behavior.

Reference: [WordPress custom endpoints](https://developer.wordpress.org/rest-api/extending-the-rest-api/adding-custom-endpoints/), [custom post type options](https://developer.wordpress.org/reference/functions/register_post_type/).
